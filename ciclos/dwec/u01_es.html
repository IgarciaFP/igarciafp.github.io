Componentes, capas y flujo de una aplicación web en el navegador

1. Tecnología Web

1.1. La World Wide Web

A menudo se confunde Internet con la Web, pero esta no existía desde el principio de Internet. Otros servicios como el correo electrónico, IRC, telnet, FTP, etc llegaron mucho antes.

En 1989, Tim Berners-Lee trabajaba en el CERN. Los científicos necesitaban compartir documentos entre ordenadores distintos. Su propuesta fue conectarlos mediante enlaces en hipertexto: desde un documento se podría saltar a otro sin tener que conocer cómo estaba organizado el equipo que lo guardaba, así tomó forma la propuesta de la Web. El hipertexto era anterior: Ted Nelson acuñó el término en 1965.

A finales de 1990 ya funcionaban el primer servidor y el primer navegador, llamado WorldWideWeb y renombrado después Nexus. Este programa también permitía editar páginas. El proyecto reunía tres piezas: HTML para organizar documentos, direcciones para localizar recursos y HTTP para pedirlos y recibirlos. El navegador de modo línea extendió el acceso a otros equipos.

En 1993, Mosaic ayudó a popularizar la navegación gráfica con texto e imágenes. Ese mismo año, el CERN puso el software de la Web en el dominio público. Netscape Navigator llegó en 1994 e Internet Explorer en 1995. La Web pasó de conectar documentos a alojar periódicos, tiendas, aplicaciones, etc.

A su vez, la fiera competencia por dominar el mercado de la incipiente World Wide Web desató la conocida como “Guerra de los Navegadores”.

1.2. Internet y Web: dos conceptos relacionados

Internet es la red de redes que comunica equipos. La World Wide Web, o WWW, es uno de los servicios que funciona sobre ella, pero no es el único. Por ejemplo, el correo electrónico también utiliza Internet, pero no es obligatorio que utilice una interfaz Web.

Por otro lado, convienen diferenciar que un navegador, por su parte, es el programa que usamos para visitar páginas; un buscador es un servicio que ayuda a encontrarlas.

1.3. Arquitectura cliente-servidor

La arquitectura cliente-servidor divide una aplicación en dos partes:

  • Cliente / frontend: interfaz que usa la persona, por ejemplo, una web o app. Muestra información y envía solicitudes.

  • Servidor / backend: recibe esas solicitudes, aplica la lógica del sistema, consulta bases de datos y devuelve respuestas.

Imagina el mostrador de una biblioteca. Tú pides un libro y la persona encargada comprueba si está disponible. En una aplicación web, el cliente inicia la petición y el servidor la atiende. La comparación sirve para entender los papeles, aunque en la red todo se intercambia mediante mensajes.

El navegador es el cliente de nuestro ejemplo. Muestra un formulario y recoge el título que escribes. El servidor busca coincidencias y devuelve los resultados. La base de datos puede guardar el catálogo, pero es la aplicación del servidor la que decide cómo consultarlo.

Servidor: backend

Una página no suele llegar como una única pieza. Primero puede descargarse HTML; después, CSS, JavaScript, imágenes y datos. El navegador reúne estos recursos para construir lo que ves.

2. El navegador Web

Un navegador web es un programa que actúa como cliente o user agent de la Web. Entre sus responsabilidades se encuentran solicitar recursos, procesar documentos HTML, aplicar CSS, ejecutar JavaScript, representar el resultado gráficamente, permitir la interacción con el usuario y proporcionar APIs y mecanismos de almacenamiento a las aplicaciones web.

Una aplicación web del lado cliente es código y recursos que el navegador obtiene, interpreta, ejecuta y representa dentro de un entorno controlado.

HTTP define un modelo cliente-servidor en el que las peticiones son iniciadas normalmente por un navegador.

2.1. Motores de renderizado y motores JavaScript

No debemos confundir un navegador con sus motores internos.

En las principales familias actuales:

Chromium denomina Blink a su motor de renderizado; V8 se define oficialmente como el motor JavaScript y WebAssembly de Google utilizado en Chrome.

Mozilla define Gecko como su motor web, encargado entre otras cosas del análisis y representación HTML, red y DOM, y SpiderMonkey como la implementación JavaScript y WebAssembly utilizada por Firefox.

Apple/WebKit define WebKit como el motor web utilizado por Safari, mientras que JavaScriptCore es el motor JavaScript incluido en WebKit e implementa ECMAScript.

Por tanto, con el ejemplo de Chromium:

Chrome ≠ Blink ≠ V8
Chrome             aplicación/navegador
Blink              	motor web
V8                 	motor JavaScript

La distinción será útil más adelante al estudiar por qué una misma aplicación puede mostrar diferencias entre navegadores o por qué una característica de JavaScript puede depender de la versión del motor.

2.2. El DOM

El DOM —Document Object Model— es una representación en memoria de la estructura del documento. MDN explica que conecta la página con los scripts al representar documentos como HTML mediante una estructura en memoria. El DOM no es simplemente «el código HTML»: es el modelo de objetos que el navegador construye y que puede cambiar mientras la aplicación se ejecuta.

El DOM también proporciona la base para eventos y para muchas de las APIs que relacionan JavaScript con los documentos.

2.3. Compatibilidad entre navegadores

La Web se apoya en estándares comunes, pero sus implementaciones evolucionan de manera independiente. Una característica puede llegar en versiones distintas o necesitar correcciones. Como ejemplo fechado, WebKit anunció el 24 de marzo de 2026 nuevas funciones y correcciones para Safari 26.4. No es una referencia a la versión más reciente.

Por ello, la estrategia correcta no es:

"Funciona en mi navegador → funciona en todos."

sino:

1. Usar tecnologías estandarizadas.
2. Consultar compatibilidad documentada.
3. Probar en más de un motor.
4. Evitar depender innecesariamente de comportamientos propietarios.
5. Diseñar alternativas cuando una característica lo requiera.

MDN incluye tablas de compatibilidad por navegador en la documentación de las APIs; por ejemplo, su página de localStorage lo clasifica como una característica ampliamente disponible y ofrece la tabla correspondiente.

3. Protocolo HTTP

Un protocolo es un conjunto de reglas que permite que dos sistemas se comuniquen de forma compatible. En la web, el cliente solicita información o servicios y el servidor procesa la solicitud y devuelve una respuesta.

HTTP significa Hypertext Transfer Protocol, o Protocolo de transferencia de hipertexto. Establece cómo se intercambia información entre clientes y servidores web.

El ciclo básico consta de una solicitud (request) del cliente y una respuesta (response) del servidor. Por ejemplo, el navegador pide una página y el servidor envía su contenido o comunica un error.

HTTP es un protocolo de capa de aplicación basado en un modelo cliente-servidor. El navegador envía peticiones y el servidor devuelve respuestas que pueden contener HTML, CSS, JavaScript, imágenes o datos.

En este apartado basta con reconocer que una comunicación HTTP contiene información de control en forma de cabeceras y que estas aparecen tanto en peticiones como en respuestas.

HTTP define cómo intercambian mensajes cliente y servidor; HTTPS protege esa comunicación mediante TLS.

3.2. Solicitud HTTP: request

Es el mensaje que el cliente envía al servidor para solicitar una operación sobre un recurso.

Elemento

Función

Método

Indica la operación: consultar, crear, modificar o eliminar.

URL

Identifica el recurso o endpoint al que se dirige la solicitud.

Cabeceras

Contienen metadatos sobre la petición.

Cuerpo

Contiene los datos enviados; es opcional.

Ejemplo de petición

POST /alumnos HTTP/1.1
Host: ejemplo.com
Content-Type: application/json
{
"nombre": "Ana",
"edad": 16
}

POST indica la operación; /alumnos identifica el recurso; Host y Content-Type son cabeceras. El objeto JSON forma el cuerpo y contiene los datos del alumno.

3.3. Respuesta HTTP: response

Es el mensaje que devuelve el servidor al procesar una solicitud. Incluye un código de estado, cabeceras y, cuando corresponde, un cuerpo con los datos solicitados o información del resultado.

HTTP/1.1 200 OK
Content-Type: application/json
{
"id": 25,
"nombre": "Ana",
"edad": 16
}

Este ejemplo representa una consulta atendida correctamente. Los datos se devuelven en formato JSON dentro del cuerpo.

4. Cabeceras HTTP y estructura de los mensajes

Las cabeceras son campos de la forma nombre: valor que acompañan a peticiones y respuestas. Aportan metadatos sobre el contenido y las condiciones del intercambio: formato, autenticación, idioma, caché o cookies. El recurso principal suele encontrarse en el cuerpo, no en las cabeceras.

Ejemplo de petición HTTP/1.1

GET /api/alumnos/42 HTTP/1.1
Host: ejemplo.com
Accept: application/json
Authorization: Bearer token-de-ejemplo
User-Agent: ClienteAula/1.0

La primera línea contiene el método, el destino de la petición y la versión del protocolo. Después aparecen las cabeceras. Una línea en blanco las separa del cuerpo, si existe. Esta petición GET no incluye cuerpo.

POST /api/alumnos HTTP/1.1
Host: ejemplo.com
Content-Type: application/json
Content-Length: 34
{"nombre":"Ana","curso":"4º ESO"}

En el segundo ejemplo, el cuerpo ocupa exactamente 34 bytes en UTF-8, sin un salto de línea final. Content-Length cuenta bytes, no caracteres: el símbolo «º» ocupa dos bytes en UTF-8. En aplicaciones reales conviene dejar este cálculo a la biblioteca HTTP.

4.3. Códigos de respuesta HTTP

Cada respuesta tiene un código de estado de tres cifras que resume el resultado. En HTTP/1.1 aparece en la línea inicial, antes de las cabeceras:

HTTP/1.1 200 OK
Content-Type: application/json

HTTP/1.1 es la versión; 200, el código; OK, una frase descriptiva. El número determina el significado. En HTTP/2 y HTTP/3 se transmite mediante :status, sin esa línea textual.

Familia

Significado

Ejemplos

1xx

Información provisional

100 Continue

2xx

Operación correcta

200 OK; 201 Created

3xx

 Redirección o acción adicional; incluye revalidación

301 Moved Permanently

4xx

Error relacionado con la petición

400 Bad Request; 404 Not Found

5xx

Error del servidor

500 Internal Server Error

Como primera aproximación, 200 OK indica una petición atendida correctamente y 404 Not Found que no se encontró el recurso o no se revela su existencia. El catálogo completo se desarrolla más adelante.

Si un cliente no reconoce un código concreto, lo interpreta según su familia. Las respuestas 1xx preceden normalmente a una respuesta final. Un error DNS, TLS o de conexión puede ocurrir antes de recibir cualquier código HTTP.

4.4. Gestión de la caché

La caché web guarda respuestas HTTP para reutilizarlas en peticiones posteriores. Así reduce descargas, latencia y trabajo del servidor.

Cuando estamos en desarrollo, sin embargo, la caché puede ser un gran problema, ya que podemos estar viendo datos sin actualizar si utilizamos caché.

Dónde se almacena la caché

Una misma petición puede encontrarse con varias capas:

Capa

Qué almacena y para quién

Navegador

Respuestas en memoria o disco para ese usuario. Es una caché privada.

Proxy compartido

Respuestas reutilizables por varios usuarios.

CDN o proxy inverso

Respuestas cerca del usuario o delante del servidor de origen.

Aplicación

Resultados de consultas, fragmentos o páginas; tiene reglas propias.

Service worker

Respuestas gestionadas mediante JavaScript y la API Cache.

Cada recurso tiene su propia política: el HTML, su CSS, los scripts y las imágenes son respuestas independientes. Poner no-store al HTML no transmite esa política a sus imágenes.

HTTPS permite caché en el navegador y en una CDN que termina la conexión TLS; un intermediario que solamente transporta tráfico cifrado no puede inspeccionarlo para cachearlo.

Cómo decide si puede reutilizar una respuesta

La caché busca una respuesta correspondiente al método y la URL, considerando también las variantes indicadas por Vary.

Después distingue:

  • No existe copia: solicita el recurso.

  • Existe y está fresca: normalmente puede reutilizarla sin consultar.

  • Ha caducado: puede revalidarla; que esté caducada no significa que haya cambiado ni que se haya borrado.

  • La política exige validación: consulta antes de reutilizarla, aunque acabe de almacenarla.

La frescura depende de la edad de la respuesta y del tiempo permitido. Age refleja su edad estimada: pasar por otra caché no reinicia automáticamente el plazo. Además, una caché puede desalojar una copia antes por falta de espacio. El tiempo de frescura no garantiza tiempo de almacenamiento.

El control principal se realiza mediante cabeceras HTTP.

La caché conserva respuestas para reutilizarlas. Hay cachés privadas, como la del navegador, y compartidas, como ciertos proxies y CDN. Las reglas deben evitar que datos personales se reutilicen para otros usuarios.

HTTP/1.1 200 OK
Cache-Control: max-age=3600
ETag: "imagen-v3"
Content-Type: image/png

La respuesta puede considerarse fresca durante 3600 segundos, según su edad y las reglas de caché. Cuando necesita revalidarse, el cliente puede enviar:

GET /logo.png HTTP/1.1
Host: ejemplo.com
If-None-Match: "imagen-v3"

Si la representación no cambió, el servidor puede responder 304 Not Modified, sin cuerpo. El cliente reutiliza el contenido almacenado. Si cambió, normalmente recibe 200 con el nuevo contenido y un nuevo validador.

Directiva de Cache-Control

Significado

max-age=3600

Define un tiempo de frescura de una hora

no-cache

Permite almacenar, pero exige revalidar antes de reutilizar

no-store

Indica que no debe almacenarse la respuesta

private

Impide almacenarla en cachés compartidas

public

Autoriza almacenamiento compartido bajo las reglas aplicables

Importante: no-cache no significa «no guardar». Para prohibir el almacenamiento se utiliza no-store. ETag es un validador opaco: no tiene por qué ser un número de versión ni un hash.

Para recursos versionados, cambiar la URL al actualizar el contenido facilita usar caché prolongada. En datos personalizados conviene decidir explícitamente si pueden almacenarse y dónde.

4.5. CORS: acceso desde otros orígenes

CORS es el mecanismo por el que un servidor indica qué otras webs pueden leer sus respuestas desde el navegador. Significa Cross-Origin Resource Sharing: intercambio de recursos entre orígenes.

La configuración la publica el servidor mediante cabeceras HTTP, y el navegador la hace cumplir. Por eso una petición puede funcionar con curl o desde tu backend y fallar cuando la haces con JavaScript en una página. Referencia: MDN.

La política de mismo origen evita, por ejemplo, que una página maliciosa lea libremente datos de otra web donde tienes sesión iniciada. CORS permite autorizar excepciones. MDN: política de mismo origen.

  5. Detén solamente el servidor del puerto 8001 con Ctrl + C. Crea cors-lab/servidor_cors.py:

    from functools import partial
from http.server import SimpleHTTPRequestHandler, ThreadingHTTPServer

class CORSHandler(SimpleHTTPRequestHandler):
    def end_headers(self):
        self.send_header("Access-Control-Allow-Origin",
                         "http://localhost:8000")
        super().end_headers()

handler = partial(CORSHandler, directory="api")
ThreadingHTTPServer(("localhost", 8001), handler).serve_forever()

  6. Ejecuta python servidor_cors.py, recarga la mini página y vuelve a pulsar el botón. Ahora aparecerá el JSON. En Network comprueba la cabecera Access-Control-Allow-Origin: http://localhost:8000.

  7. Cambia temporalmente el puerto autorizado en Python a http://localhost:9999, reinicia el servidor y repite. Explica por qué vuelve a fallar aunque la API responda.

Conclusión esperada: CORS no impide enviar la petición; controla si el JavaScript de un origen puede leer la respuesta de otro. La autorización debe enviarla el servidor de destino.

4.6. User-Agent

Un agente de usuario es el programa que inicia una petición: navegador, aplicación, herramienta de consola, biblioteca o robot. User-Agent es la cabecera con la que ese programa declara información sobre sí mismo. No identifica a la persona que lo utiliza.

Su sintaxis permite productos con versión y comentarios. Un cliente sencillo puede enviar User-Agent: ClienteAula/1.0. Los navegadores suelen utilizar cadenas más largas por razones históricas de compatibilidad.

Anatomía de una cadena de navegador

El siguiente ejemplo está dividido visualmente para facilitar la lectura. En HTTP/1.1 se enviaría como un único campo en una línea, sin estos saltos:

Mozilla/5.0 (Windows NT 10.0; Win64; x64)
AppleWebKit/537.36 (KHTML, like Gecko)
Chrome/140.0.0.0 Safari/537.36

Fragmento

Interpretación y precaución

Mozilla/5.0

Token histórico; no significa que sea Firefox

Windows NT 10.0

Plataforma declarada; no garantiza la versión real de Windows

Win64; x64

Indicadores declarados de plataforma y arquitectura

AppleWebKit/537.36

Token de compatibilidad; no prueba que el motor actual sea WebKit

KHTML, like Gecko

Comentario histórico de compatibilidad

Chrome/140.0.0.0

Versión declarada; algunos componentes pueden estar reducidos

Safari/537.36

Token de compatibilidad; no implica que sea Safari

Chrome utiliza Blink, aunque su cadena incluya AppleWebKit. Otros navegadores basados en Chromium también pueden contener Chrome. Por tanto, buscar una palabra aislada no identifica de forma fiable el navegador. Estos tokens se acumularon para evitar que sitios con detección rígida rechazasen clientes compatibles.
