Examen de prueba: DWEC Unidad 1

Práctica de autoevaluación · No es el examen oficial

1 Explica qué tareas realiza el navegador (entorno cliente) y qué tareas realiza el servidor cuando accedes a una página web. Pon un ejemplo concreto de cada uno.

Puntos clave de la respuesta:

• Cliente (Navegador): Se encarga de solicitar los recursos, interpretar el código (HTML, CSS, JS), renderizar la interfaz en pantalla y gestionar la interacción directa con el usuario (ejemplo: mostrar un mensaje cuando se pulsa un botón).

• Servidor: Se encarga de procesar la lógica de negocio, consultar bases de datos y enviar los archivos o datos solicitados al cliente (ejemplo: comprobar en la base de datos si la contraseña introducida es correcta).

2 Sintetiza la responsabilidad de cada una de las 3 tecnologías fundamentales del cliente web: HTML, CSS y JavaScript. ¿Qué aporta cada una a la página?

Puntos clave de la respuesta:

• HTML: Aporta la estructura y el contenido semántico de la página (títulos, párrafos, formularios, imágenes).

• CSS: Aporta la presentación y el diseño visual (colores, fuentes, posiciones, adaptabilidad a pantallas).

• JavaScript: Aporta el comportamiento y la interactividad (reaccionar a eventos del usuario, modificar el contenido sin recargar, validar datos).

3 Si abres la pestaña Elements (Elementos) en las DevTools de tu navegador, puedes hacer doble clic en un texto de la web y cambiarlo. ¿Ese cambio lo está viendo todo el mundo que entra a la web? Justifica tu respuesta según el modelo cliente/servidor.

Puntos clave de la respuesta:

• No. El cambio solo se produce localmente en la memoria del navegador de tu ordenador.

• Justificación: Las DevTools modifican la copia del documento (DOM) que el cliente ha descargado. Los archivos originales del servidor no sufren ninguna modificación, por lo que los demás usuarios seguirán viendo la página original.

4 Imagina que en un formulario web obligas a que el campo "Teléfono" tenga 9 números usando JavaScript. ¿Por qué es necesario volver a comprobar ese dato en el servidor antes de guardarlo en la base de datos?

Puntos clave de la respuesta:

• Porque el cliente es un entorno no seguro y manipulable.

• Un usuario puede desactivar JavaScript en su navegador, modificar el script desde la consola de DevTools o enviar los datos directamente al servidor saltándose la página web. La validación en cliente sirve para mejorar la experiencia de usuario (rapidez), pero la validación en servidor es imprescindible por seguridad e integridad de los datos.

5 ¿Para qué sirve la pestaña Console (Consola) de las herramientas de desarrollo? Nombra dos usos habituales que le da un desarrollador web en su día a día.

Puntos clave de la respuesta:

• Definición: Es un entorno interactivo para ejecutar código JavaScript al vuelo y ver los mensajes del sistema o del propio código.

• Usos habituales:

1. Ver mensajes de error del código o impresiones de prueba mediante console.log().

2. Probar y ejecutar pequeñas instrucciones o funciones de JavaScript directamente sobre la página actual.

6 Un usuario entra en una web y las imágenes no cargan correctamente. ¿En qué pestaña de las DevTools (Network / Red o Elements / Elementos) deberías mirar para saber si el servidor está devolviendo un error al intentar descargar esas imágenes? Explica por qué.

Puntos clave de la respuesta:

• Se debe mirar en la pestaña Network (Red).

• Explicación: La pestaña Network registra todas las peticiones HTTP que el navegador envía al servidor y las respuestas recibidas. Ahí se puede comprobar el estado HTTP de la descarga de cada imagen (por ejemplo, si devuelve un error 404 de "no encontrado"). La pestaña Elements solo muestra la estructura HTML, no el tráfico de red.

7 Explica qué ventaja tiene para el usuario que una página ejecute código JavaScript en su navegador en lugar de tener que pedirle todo al servidor cada vez que hace un clic.

Puntos clave de la respuesta:

• Inmediatez / Rapidez: La interfaz responde al instante sin necesidad de recargar la página entera ni esperar el tiempo de respuesta del servidor a través de la red.

• Ahorro de tráfico: Se reduce el consumo de ancho de banda y la carga de trabajo en el servidor, ofreciendo una experiencia mucho más fluida y similar a una aplicación de escritorio o móvil.

8 En la pestaña Sources (Fuentes) de las DevTools podemos ver los archivos .js de la página. ¿Qué ocurre si un desarrollador guarda contraseñas o claves privadas dentro de sus archivos JavaScript de cliente?

Puntos clave de la respuesta:

• Es un fallo grave de seguridad. Cualquier usuario puede abrir la pestaña Sources de las DevTools, inspeccionar el código JavaScript enviado al navegador y ver las contraseñas o claves en texto plano.

• Regla: Todo lo que se envía al cliente es público. Las contraseñas de servicio y claves privadas no deben incluirse en archivos enviados al navegador; se gestionan en el servidor.

9 Explica la diferencia entre una arquitectura donde el servidor genera y envía la página HTML completa en cada clic frente a una donde el navegador solo pide datos en segundo plano y actualiza una parte de la pantalla.

Puntos clave de la respuesta:

• Modelo tradicional (Servidor): Cuando se navega o se envía un formulario que requiere una nueva página, el servidor devuelve HTML y el navegador carga ese documento. No todos los clics tienen que pedir una página.

• Modelo cliente (Dinámico / AJAX): La página puede pedir nuevos datos sin cargar otro documento. Cuando hace falta, JavaScript pide los datos necesarios en segundo plano y modifica únicamente el trozo de la pantalla que cambia, sin recargar el resto.

10 Describe el modelo de 3 capas en una aplicación web (Presentación, Negocio, Datos). Indica en cuál de las capas se sitúa el trabajo principal del desarrollador web en entorno cliente (DWEC).

Puntos clave de la respuesta:

• Capa de Presentación: La interfaz con la que interactúa el usuario (HTML/CSS/JS en el navegador).

• Capa de Negocio: Las reglas y la lógica de la aplicación (normalmente en el servidor).

• Capa de Datos: La base de datos donde se almacena la información de forma permanente.

• Ubicación de DWEC: El desarrollo cliente se centra principalmente en la Capa de Presentación y en la lógica de interfaz asociada que se ejecuta en el navegador del usuario.

11Una página en https://tienda.ejemplo pide datos con JavaScript a https://api.ejemplo. ¿Por qué puede aparecer un error CORS? ¿Quién debe permitir que la página lea la respuesta y cómo lo indica?

Puntos clave de la respuesta:

Los dos dominios tienen orígenes distintos. La política de mismo origen limita qué respuestas puede leer JavaScript.

El servidor de la API debe autorizar el origen mediante cabeceras como Access-Control-Allow-Origin; el navegador aplica esa política. En ciertos casos hay una petición previa OPTIONS (preflight).

No se arregla añadiendo esa cabecera a la petición del cliente. CORS controla la lectura desde el navegador y no sustituye la autenticación ni la autorización del servidor.

12¿Para qué sirve la caché HTTP del navegador? Explica la diferencia entre Cache-Control: no-cache y no-store, y qué significa recibir un estado 304.

Puntos clave de la respuesta:

La caché permite reutilizar respuestas para reducir descargas y tiempos de espera.

no-cache permite guardar la respuesta, pero exige validarla con el servidor antes de reutilizarla. no-store indica que no debe almacenarse.

304 Not Modified responde a una petición condicional e indica que puede reutilizarse la copia guardada; no incluye un nuevo cuerpo del recurso. Una copia fresca puede reutilizarse sin consultar al servidor, por lo que no siempre se observa un 304.

13Al abrir una URL que muestra una página HTML con CSS, JavaScript e imágenes, ¿cómo descubre el navegador esos archivos? ¿Se descargan todos uno detrás de otro? Explica también qué puede ocurrir con un script normal, defer y async.

Puntos clave de la respuesta:

Se solicita el documento HTML y, al recibirlo y analizarlo, se descubren referencias a otros recursos. El navegador puede empezar a pedirlos antes de recibir todo el HTML.

Muchas descargas pueden solaparse: no existe un orden fijo «HTML completo → CSS completo → JavaScript completo → imágenes».

Un script clásico externo sin async ni defer normalmente detiene el análisis del HTML mientras se obtiene y ejecuta. Con defer, se descarga mientras continúa el análisis y se ejecuta después, respetando el orden entre scripts diferidos. Con async, se ejecuta cuando está disponible y no garantiza el orden entre scripts.

El CSS puede retrasar el dibujado y la ejecución de ciertos scripts. Network permite observar el orden y el solapamiento reales.

14¿En qué se diferencian GET y POST? Pon un ejemplo adecuado para cada método. ¿Usar POST garantiza que los datos estén cifrados?

Puntos clave de la respuesta:

GET solicita una representación de un recurso; por ejemplo, consultar un producto. Debe usarse para operaciones de lectura, sin pedir cambios en el estado del servidor. Los parámetros suelen ir en la URL.

POST envía datos para que el servidor los procese, normalmente en el cuerpo de la petición; por ejemplo, enviar un pedido. No garantiza que repetir la petición tenga el mismo efecto.

POST no cifra los datos. HTTPS aporta la protección del transporte. Tanto GET como POST pueden utilizar HTTPS; los parámetros en una URL pueden quedar en historiales o registros.

15¿Para qué sirve el certificado que presenta un servidor al conectarnos por HTTPS? ¿Quién lo comprueba? ¿Un certificado válido garantiza que el contenido de la página sea fiable?

Puntos clave de la respuesta:

El certificado vincula una clave pública con un nombre de dominio mediante una firma que el navegador puede validar siguiendo una cadena de confianza.

El navegador comprueba, entre otras cosas, que el dominio coincide, que el certificado está dentro de su periodo de validez y que la cadena llega a una autoridad de confianza. Durante TLS el servidor demuestra que posee la clave privada correspondiente.

TLS negocia claves de sesión para proteger los datos en tránsito. El certificado ayuda a autenticar el servidor; no demuestra que el contenido sea verdadero ni que el sitio sea honesto.

16¿Quién puede establecer una cookie y dónde se guarda? Explica el papel de Set-Cookie, del navegador y de JavaScript. ¿Qué cambia si una cookie tiene el atributo HttpOnly?

Puntos clave de la respuesta:

El servidor puede pedir al navegador que guarde una cookie mediante la cabecera de respuesta Set-Cookie. JavaScript de una página también puede crear ciertas cookies mediante document.cookie, dentro de los límites del navegador.

El navegador decide si la acepta según sus políticas, la guarda y la envía en la cabecera Cookie de las peticiones que cumplan sus condiciones de dominio, ruta y otros atributos. No se envía a cualquier sitio.

HttpOnly impide leer o modificar esa cookie desde JavaScript. La establece el servidor y el navegador puede seguir enviándola automáticamente en las peticiones correspondientes.
