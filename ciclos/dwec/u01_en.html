1. Web technology

1.1. The World Wide Web

Often confused Internet with the WebOther services such as email, IRC, telnet, FTP, etc. arrived much earlier.

In 1989, Tim Berners-Lee The scientists needed to share documents between different computers. Their proposal was to connect them via links to hypertext: from one document you could jump to another without having to know how the team that kept it was organized, so the proposal of the Web took shape. The hypertext was earlier: Ted Nelson coined the term in 1965.

At the end of 1990 the first server and the first browser, called WorldWideWeb and renamed after Nexus. This program also allowed to edit pages. The project brought together three pieces: HTML to organize documents, addresses to locate resources and HTTP to request and receive them. The online browser extended access to other computers.

In 1993, Mosaic helped popularize graphic navigation with text and images. That same year, CERN put Web software in the public domain. Netscape Navigator arrived in 1994 e Internet Explorer in 1995The Web moved from connecting documents to hosting newspapers, stores, applications, etc.

In turn, fierce competition to dominate the emerging World Wide Web market unleashed the so-called “Navigators' War”.

1.3. Client-server architecture

Architecture client-server divides an application into two parts:

  • Client / frontend: interface that the person uses, for example, a web or app. It displays information and sends requests.

  • Server / backend: receive these requests, apply system logic, consult databases and return responses.

Imagine the counter of a library. You order a book and the person in charge checks if it is available. In a web application, the client initiates the request and the server attends it. The comparison serves to understand the papers, although in the network everything is exchanged through messages.

The browser is the client of our example. It shows a form and collects the title you write. The server searches for matches and returns the results. The database can save the catalog, but it is the server application that decides how to consult it.

2.1. JavaScript render engines and engines

We should not confuse a browser with its internal engines.

In today's main families:

2.2. The DOM

The DOM —Document Object Model — is a memory representation of the document structure. MDN explains that it connects the page to scripts by representing documents as HTML by means of a memory structure. The DOM is not simply "the HTML code": it is the model of objects that the browser builds and that can change while the application is running.

The DOM also provides the basis for events and for many of the APIs that link JavaScript to documents.

3. HTTP Protocol

A protocol is a set of rules that allows two systems to communicate in a compatible way. On the web, the client requests information or services and the server processes the request and returns a response.

HTTP means Hypertext Transfer Protocol, or Hypertext Transfer Protocol. Sets how information is exchanged between clients and web servers.

The basic cycle consists of a request from the client and a response from the server. For example, the browser asks for a page and the server sends its content or communicates an error.

HTTP is a protocol of Application layer model-based client-server. The browser sends requests and the server returns responses that may contain HTML, CSS, JavaScript, images or data.

3.2. HTTP request: request

It is the message that the client sends to the server to request an operation on a resource.

POST /alumnos HTTP/1.1

POST indicates the operation; /students identifies the resource; Host and Content-Type are headers. The JSON object forms the body and contains the student data.

3.3. HTTP response: response

It is the message that the server returns when processing a request. It includes a status code, headers and, where applicable, a body with requested data or result information.

HTTP/1.1 200 OK
Content-Type: application/json
{
"id": 25,
"nombre": "Ana",
"edad": 16
}

This example represents a correctly viewed query. Data is returned in JSON format within the body.

4. HTTP headers and message structure

Headers are name form fields: value that accompany requests and responses. They provide metadata about the content and terms of the exchange: format, authentication, language, cache or cookies. The main resource is usually found in the body, not in the headers.

Example of HTTP/1.1 request

GET /api/alumnos/42 HTTP/1.1
Host: ejemplo.com
Accept: application/json
Authorization: Bearer token-de-ejemplo
User-Agent: ClienteAula/1.0

The first line contains the method, the destination of the request and the version of the protocol. Then the headers appear. A blank line separates them from the body, if any. This GET request does not include body.

POST /api/alumnos HTTP/1.1
Host: ejemplo.com
Content-Type: application/json
Content-Length: 34
{"nombre":"Ana","curso":"4º ESO"}

In the second example, the body occupies exactly 34 bytes in UTF-8, without a final line jump. Content-Length counts bytes, not characters: the symbol ‘o’ occupies two bytes in UTF-8. In real applications, this calculation should be left to the HTTP library.

4.3. HTTP response codes

Each response has a three-digit status code that summarizes the result. In HTTP/1.1 it appears in the initial line, before the headers:

HTTP/1.1 200 OK
Content-Type: application/json

HTTP/1.1 is the version; 200, the code; OK, a descriptive phrase. The number determines the meaning. In HTTP/2 and HTTP/3 it is transmitted by :status, without that text line.

Family

Meaning

Examples

1xx

Provisional information

100 Continue

2xx

Correct operation

200 OK; 201 Created

3xx

 Redirection or additional action; includes revalidation

301 Moved Permanently

4xx

Request-related error

400 Bad Request; 404 Not Found

5xx

Server Error

500 Internal Server Error

As a first approximation, 200 OK indicates a correctly answered request and 404 Not Found that the resource was not found or its existence is not revealed. The complete catalog is developed later.

If a client does not recognize a particular code, it interprets it according to his family. 1xx responses usually precede a final response. A DNS, TLS or connection error can occur before receiving any HTTP code.

4.4. Cache management

The Web cache saves HTTP responses for reuse in subsequent requests. This reduces downloads, latency and server work.

When we are developing, however, the cache It can be a big problem.since we may be viewing data without updating if we use cache.

Where the cache is stored

The same request can be found with several layers:

Layer

What it stores and for whom

Browser

Answers in memory or disk for that user. It is a private cache.

Shared Proxy

Reusable responses by several users.

CDN or reverse proxy

Answers near the user or in front of the source server.

Implementation

Results of queries, excerpts or pages; has own rules.

Service worker

Answers managed using JavaScript and the Cache API.

Each resource has its own policy: HTML, its CSS, scripts and images are independent responses. Putting no-store to HTML does not transmit that policy to your images.

HTTPS allows caches in the browser and in a CDN that terminates the TLS connection; an intermediary that only transports encrypted traffic cannot inspect it to search it.

How you decide if you can reuse an answer

The cache looks for a response corresponding to the method and URL, also considering the variants indicated by Vary.

Then he distinguishes:

  • No copy available: request the appeal.

  • It exists and is fresh: you can usually reuse it without consulting.

  • It's expired: it can be revalidated; its expiry does not mean that it has changed or that it has been deleted.

  • The policy requires validation: consult before reuse, even if you have just stored it.

The freshness depends on the age of the response and the time allowed. Age reflects your estimated age: going through another cache does not automatically restart the deadline. In addition, a cache can evict a copy earlier due to lack of space. The freshness time does not guarantee storage time.

The main control is done using HTTP headers.

The cache retains answers to reuse them. There are private caches, such as browser caches, and shared, such as certain proxies and CDNs. Rules should preventing personal data from being reused for other users.

HTTP/1.1 200 OK
Cache-Control: max-age=3600
ETag: "imagen-v3"
Content-Type: image/png

The answer can be considered fresh for 3600 seconds, depending on your age and cache rules. When you need to be revalidated, the customer can send:

GET /logo.png HTTP/1.1
Host: ejemplo.com
If-None-Match: "imagen-v3"

If the representation did not change, the server can respond 304 Not Modified, bodyless. The client reuses the stored content. If changed, it usually receives 200 with the new content and a new validator.

Cache-Control Directive

Meaning

max-age=3600

Define a time of freshness of one hour

no-cache

Allows storage, but requires revalidation before reuse

no-store

Indicates that the answer should not be stored

private

Prevents storing it in shared caches

public

Authorizes shared storage under applicable rules

Important: no-cache does not mean "do not save". To prohibit storage, non-store is used. ETag is an opaque validator: it does not have to be a version number or a hash.

For versioned resources, change the URL when updating content makes it easy to use extended cache. In custom data it is important to explicitly decide whether and where they can be stored.

4.5. CORS: access from other sources

CORS is the mechanism by which a server indicates which other websites can read their responses from the browser. It means Cross-Orgin Resource Sharing: exchange of resources between sources.

The configuration is published by the server via HTTP headers, and is enforced by the browser. Therefore, a request can work with curl or from your backend and fail when you do it with JavaScript on a page. Reference: MDN.

The policy of the same origin prevents, for example, that a malicious page freely reads data from another website where you are logged in. CORS allows to authorize exceptions. MDN: policy of the same origin.

Simple example: observe and fix a CORS error

You need to have Node.js installed. Create a folder cors-simple with these two files.

1. File datos.json

{"mensaje": "¡La petición funciona!"}

2. File index.html

<button id="boton">Pedir datos</button>

<script>
boton.onclick = () => {
  fetch("http://localhost:8001/datos.json")
    .then(respuesta => respuesta.json())
    .then(datos => salida.textContent = datos.mensaje)
    .catch(error => salida.textContent = "Error CORS");
};
</script>

3. Causes error

Opens two terminals within cors-simple and executes:

# Terminal 1: sirve la página
npx http-server -p 8000

# Terminal 2: sirve el JSON sin permiso CORS
npx http-server -p 8001

Visit http://localhost:8000, open the Console of the DevTools and press Requesting data. The page belongs to the origin http://localhost:8000 and the JSON to http://localhost:8001. Since the second server does not give permission to the first, the CORS error appears.

4. Solution

Stop the second terminal with Ctrl + C and restarts only the JSON server with the option --cors:

npx http-server -p 8001 --cors

Reload the page and press the button again. Now it will appear "The request works!" Network, select datos.json and check that the answer contains Access-Control-Allow-Origin: *.

4.6. User-Agent

A user agent is the program that starts a request: browser, app, console tool, library or robot. User-Agent is the header with which that program declares information about itself. It does not identify the person who uses it.

Its syntax allows products with version and comments. A simple customer can send User-Agent: ClientAula/1.0. Browsers usually use longer strings for historical compatibility reasons.

Anatomy of a browser string

Next example is visually divided to facilitate reading. In HTTP/1.1 it would be sent as a single field on a line, without these jumps:

Mozilla/5.0 (Windows NT 10.0; Win64; x64)
AppleWebKit/537.36 (KHTML, like Gecko)
Chrome/140.0.0.0 Safari/537.36

Fragment

Interpretation and caution

Mozilla/5.0

Historical Token; does not mean it is Firefox

Windows NT 10.0

Platform declared; does not guarantee the actual version of Windows

Win64; x64

Declared platform and architecture indicators

AppleWebKit/537.36

Token compatibility; does not prove that the current engine is WebKit

KHTML, like Gecko

Historical compatibility comment

Chrome/140.0.0.0

Declared version; some components may be reduced

Safari/537.36

Token compatibility; does not imply Safari

Chrome uses Blink, even if its string includes AppleWebKit. Other Chromium-based browsers can also contain Chrome. Therefore, searching for an isolated word does not reliably identify the browser. These tokens were accumulated to prevent hard-detected sites from rejecting supported customers.
