Tema 1: Planificación y Diseño de Interfaces Web

1. Introducción al Diseño Web

El desarrollo de aplicaciones digitales modernas exige concebir la interacción con las personas antes de escribir cualquier línea de código de servidor o de base de datos. En este tema se estudian los fundamentos teóricos, metodológicos y visuales de la planificación de interfaces de usuario (User Interface o UI) y la experiencia de usuario (User Experience o UX).

1.1. Evolución histórica del diseño web

El diseño web no ha evolucionado únicamente por cambios estéticos. Cada etapa responde a nuevas capacidades técnicas, dispositivos, velocidades de conexión y expectativas de uso. La Web pasó de organizar documentos enlazados y casi exclusivamente textuales a ofrecer aplicaciones interactivas, accesibles, adaptativas e incluso inmersivas. Comprender esta evolución permite distinguir una tendencia visual de una mejora real en comunicación, usabilidad o rendimiento.

2. Interacción Persona-Ordenador

2.1. Fundamentos de Interfaz de Usuario (UI) e Interacción Persona-Ordenador (IPO/HCI)

2.1.1. Definición y alcance de la UI (Interfaces Gráficas - GUI)

Las Interfaces de Usuario (User Interfaces o UI) engloban el conjunto de elementos hardware y software que actúan como frontera de comunicación entre el ser humano y las máquinas. En el ecosistema del diseño digital, la interfaz abarca pantallas, ventanas, menús, controles, iconografía, documentación y sistemas de ayuda en línea.

Históricamente, la interacción se basaba en interfaces de línea de comandos (CLI, Command Line Interface) estructuradas bajo un patrón Acción-Objeto, donde la persona primero indicaba el comando y después el archivo u objeto a modificar. Con la primera implantación comercial por parte de Xerox en 1981 y su posterior popularización a través de Apple, surgieron las Interfaces Gráficas de Usuario (GUI, Graphical User Interfaces).

Las GUI revolucionaron el sector introduciendo la tecnología WYSIWYG (What You See Is What You Get, lo que ves es lo que obtienes) y el paradigma de interacción Objeto-Acción. En este modelo, la persona selecciona primero el objeto visual en pantalla (por ejemplo, un archivo o una imagen) y posteriormente ejecuta la acción deseada sobre él (como eliminar, mover o editar).

2.1.2. Interacción Persona-Ordenador (IPO / HCI)

La Interacción Persona-Ordenador (IPO, o HCI por sus siglas en inglés Human-Computer Interaction) es la disciplina encargada de estudiar cómo los seres humanos interactúan con las tecnologías informáticas. Su objetivo fundamental es lograr que los sistemas sean eficientes, seguros e intuitivos.

2.2. User Interface (UI) vs. User Experience (UX)

2.2.1. Diferenciación técnica entre UI y UX

En la industria del software es habitual confundir los conceptos de UI y UX, aunque representan planos complementarios:

  • User Interface (UI): Se enfoca en la creación de los componentes visuales e interactivos de la pantalla (botones, tipografías, colores, maquetación HTML/CSS).
  • User Experience (UX): Hace referencia a la experiencia global y al grado de usabilidad percibido por la persona al interactuar con el sistema digital. Engloba emociones, arquitectura de información y diseño de interacción (IxD).
«Algo que luce genial pero es difícil de usar representa una gran UI con una pobre UX. Mientras que algo muy usable que luce terrible es ejemplo de una gran UX con una pobre UI» — Helga Moreno.

2.3. Usabilidad y accesibilidad

2.3.1. Atributos clave y perfiles de usuario

La usabilidad define la medida en que el diseño de una interfaz toma en consideración la psicología y fisiología humanas para lograr que el uso del sistema resulte efectivo, eficiente y satisfactorio.

Atributo de Usabilidad Descripción Técnica
Curva de aprendizaje Facilidad con la que los usuarios novatos se adaptan al sistema y ejecutan tareas básicas.
Eficiencia de uso Rapidez con la que los usuarios experimentados ejecutan sus objetivos tras dominar la interfaz.
Porcentaje de errores Frecuencia y gravedad de las equivocaciones cometidas; afecta directamente a la frustración.
Facilidad para recordar Capacidad de reutilizar el sistema con éxito tras un período de inactividad sin re-aprenderlo.
Satisfacción del usuario Sensación subjetiva de comodidad, utilidad y agradabilidad tras la interacción.

2.3.2. Usabilidad vs Accesibilidad

La Usabilidad optimiza la experiencia para un perfil de usuario determinado dentro de un contexto de uso. Por su parte, la Accesibilidad Web asegura que los contenidos digitales sean utilizables por todas las personas, independientemente de sus capacidades físicas, sensoriales o cognitivas, o de las tecnologías de asistencia empleadas (lectores de pantalla, teclados adaptados).

2.3.3. Principios prácticos de usabilidad centrada en el usuario

Diseñar con el usuario en el centro implica comprobar de forma continua cómo cada decisión afecta a la eficacia, la eficiencia y la satisfacción. Los siguientes principios sirven como guía para diseñar y auditar aplicaciones web; deben aplicarse según las tareas, el público y el contexto real de uso.

Principio Aplicación en la interfaz Ejemplo
1. Respuesta ágil
Regla orientativa de los dos segundos		 Optimizar la carga y evitar esperas innecesarias. Si una operación no puede completarse de inmediato, confirmar que el sistema está trabajando. Mostrar el contenido principal con rapidez y cargar después los elementos secundarios.
2. Feedback de información Comunicar el resultado y el estado de cada acción mediante mensajes, cambios visuales o indicadores de progreso. Tras enviar un formulario, desactivar temporalmente el botón, mostrar progreso y confirmar el envío.
3. Funcionalidad con valor real Eliminar controles, contenidos y servicios que no contribuyan a las tareas del usuario ni a los objetivos del producto. No incluir un calendario o un widget meteorológico en una tienda si no intervienen en la compra.
4. Espacio entre elementos Usar espacio en blanco para separar grupos, reducir ruido visual y facilitar la exploración. Agrupar los datos de envío y pago en bloques diferenciados dentro del proceso de compra.
5. Legibilidad de los textos Cuidar tipografía, tamaño, contraste, longitud de línea, interlineado y estructura mediante títulos y párrafos breves. Texto de cuerpo adaptable, contraste mínimo WCAG y líneas de lectura que no ocupen toda una pantalla ancha.
6. Coherencia y consistencia Mantener patrones estables de color, iconografía, terminología, distribución y comportamiento. Utilizar siempre el mismo color y formato para errores, avisos, confirmaciones y acciones principales.
7. Acceso directo al contenido
Regla orientativa de los tres clics		 Reducir pasos innecesarios y situar las funciones frecuentes en rutas visibles y comprensibles. Permitir acceder al seguimiento de un pedido desde la cuenta y también desde el correo de confirmación.
8. Manejo y recuperación de errores Prevenir errores cuando sea posible y ofrecer mensajes comprensibles, causas y acciones de recuperación. Una página 404 mantiene la identidad del sitio y ofrece búsqueda, inicio y enlaces útiles.
9. Carga cognitiva controlada
Principio del 7 ± 2		 Agrupar opciones relacionadas y presentar la información por etapas para no exigir que se recuerden demasiados elementos simultáneamente. Organizar un menú extenso en categorías reconocibles en lugar de mostrar una lista plana.
10. Protección del trabajo Conservar datos y permitir deshacer, recuperar o continuar una tarea interrumpida. Guardar automáticamente un borrador y mantener el carrito después de un error de pago.
11. Correspondencia con el mundo real Emplear palabras, secuencias y convenciones familiares para el público objetivo. En una biblioteca, usar “préstamos”, “renovar” y “devolver” en lugar de códigos internos del sistema.
12. Curva de aprendizaje mínima Aprovechar patrones conocidos, revelar la complejidad progresivamente y ofrecer ayuda contextual. Identificar la búsqueda con una lupa acompañada por una etiqueta clara.
13. Navegación rápida entre secciones Ofrecer orientación, rutas de retorno y mecanismos adecuados al volumen de contenidos. Combinar menú principal, migas de pan, búsqueda, paginación y estado de la sección activa.
14. Simetría y asimetría intencionales Usar la simetría para aportar equilibrio y la asimetría para dirigir la atención sin romper la jerarquía. Destacar una llamada a la acción mediante tamaño o color dentro de una composición estable.
Reglas orientativas que deben validarse

Los valores de dos segundos, tres clics y 7 ± 2 elementos ayudan a detectar posibles problemas, pero no son criterios normativos ni límites universales. El número de clics importa menos que la claridad de cada paso, y el trabajo de Miller estudia la memoria inmediata, no establece un máximo obligatorio de opciones de menú. Las decisiones deben comprobarse mediante analítica, pruebas de rendimiento y tests con usuarios.

3. Elementos del Diseño Gráfico Aplicados a la Web

El diseño de interfaces articula cuatro grupos de elementos complementarios:

  • Elementos conceptuales: Punto, Línea, Plano y Volumen (formas abstractas no físicas).
  • Elementos visuales: Forma, Medida, Color, Textura y Tipografía (lo que se percibe en pantalla).
  • Elementos de relación: Dirección, Posición, Espacio y Gravedad visual (gobiernan la distribución).
  • Elementos prácticos: Representación, Significado y Función (propósito de comunicación).

3.1. Elementos conceptuales

Los elementos conceptuales definen la estructura: el punto señala una posición; la línea separa o guía; el plano delimita una superficie; y el volumen aporta profundidad, sugerida en pantalla con sombras y superposiciones.

3.2. Elementos visuales

La forma identifica los elementos; la medida establece su importancia; el color diferencia y comunica; la textura caracteriza las superficies; y la tipografía organiza la lectura. Usa estos atributos con coherencia y acompaña los estados de color con texto o símbolos.

3.3. Elementos de relación: dirección, posición, espacio y gravedad

Los elementos de relación organizan los componentes y guían la atención. Su distribución debe seguir siendo clara al adaptar la interfaz a distintas pantallas.

3.4. Elementos prácticos

La representación es lo que muestra un elemento; el significado, lo que comunica; y la función, para qué sirve. En un botón, el icono, la etiqueta y la acción deben ser coherentes.

3.5. Sistemas de diseño y metodología Atomic Design

En el desarrollo frontend moderno no se construyen páginas aisladas, sino Sistemas de Diseño (Design Systems) escalables basados en la metodología Atomic Design (Brad Frost). Esta metodología divide la UI en 5 niveles jerárquicos:

Figura 1.5: Niveles metodológicos de Atomic Design (Brad Frost).
  • Átomos: Elementos UI indivisibles (botones, inputs, etiquetas, iconos).
  • Moléculas: Grupos de átomos unidos que ejecutan una función básica (ej. un input + un botón = formulario de búsqueda).
  • Organismos: Conjuntos de moléculas que forman una sección completa (ej. la cabecera completa o una tarjeta de producto).
  • Plantillas (Templates): Maquetación estructural (layout) sin datos reales.
  • Páginas: Instancia final del sistema rellena con contenido real para producción.
Relación entre identidad visual y Atomic Design

La identidad se traduce al sistema descrito en el apartado 3.5 mediante Design Tokens —color, tipografía, espaciado y forma— y mediante átomos como logotipo, iconos y botones. Así, la marca se mantiene coherente en todas las moléculas, organismos, plantillas y páginas.

3.5.1. Design Tokens: La base del desarrollo ágil e interoperable

Los Design Tokens (tokens de diseño) son variables agnósticas a la plataforma que almacenan los valores visuales fundamentales de un sistema de diseño —tales como códigos cromáticos en hexadecimal, tamaños tipográficos en rem, espaciados en píxeles, radios de borde y duraciones de animación. Actúan como la fuente única de verdad (Single Source of Truth) que conecta el diseño visual creado en herramientas como Figma con la implementación en código frontend (CSS, Sass, React, iOS, Android).

Figura 1.5.1: Estructura por capas de los Design Tokens: de valores globales puros a tokens semánticos e integración en código.

Los tokens se organizan habitualmente en tres niveles de abstracción:

  • Tokens Globales (o primitivos): Valores de base. En Bootstrap 5.3, --bs-blue: #0d6efd y --bs-red: #dc3545 representan colores de la paleta.
  • Tokens Semánticos: Asignan un propósito al valor. Bootstrap utiliza --bs-primary para el color principal y --bs-danger para situaciones de peligro o error; en el tema predeterminado valen #0d6efd y #dc3545, respectivamente.
  • Tokens de Componente: Controlan propiedades de un componente concreto. En los botones de Bootstrap, --bs-btn-bg define el fondo, --bs-btn-color el texto y --bs-btn-hover-bg el fondo al pasar el puntero.

Esta clasificación permite interpretar las variables de Bootstrap como tokens. Su CSS compilado no enlaza necesariamente todos los valores mediante var(): cambiar --bs-primary no actualiza por sí solo todas las variantes de botones.

Centralizar los valores facilita mantener un diseño coherente. En Bootstrap, personaliza las variables del componente o recompila las variables Sass del tema según el alcance del cambio; revisa también los estados de interacción y sus contrastes.

Ejemplo: Aplicación de Atomic Design y Design Tokens

Situación: Una empresa requiere unificar los estilos de 3 aplicaciones web distintas construidas por equipos independientes.

Desarrollo razonado: Se crea un sistema de Design Tokens centralizado en un archivo CSS con variables (--color-primary: #1e3a8a, --btn-radius: 6px). Siguiendo Atomic Design, se empaquetan los botones como átomos y las barras de búsqueda como moléculas reutilizables.

Resultado: Los equipos comparten valores y componentes, lo que facilita mantener la coherencia. Al modificar un token, deben revisar las pantallas afectadas y comprobar el contraste y los estados.

3.5.2. Ejemplo: CSS tradicional y Tailwind CSS

A diferencia de frameworks como Bootstrap o Bulma, que ofrecen componentes prediseñados —por ejemplo, .btn y .card en Bootstrap, o .button y .card en Bulma—, Tailwind CSS proporciona clases utilitarias de bajo nivel, también llamadas clases atómicas. Clases como bg-blue-500, pt-4 o text-center permiten aplicar estilos de propósito concreto combinándolas directamente en el HTML.

Relación con Atomic Design

Atomic Design organiza componentes de interfaz en átomos, moléculas, organismos, plantillas y páginas. El enfoque de clases utilitarias de Tailwind determina cómo se escriben sus estilos. Son conceptos distintos y compatibles: un botón es un átomo de la interfaz, mientras que bg-blue-500 es una utilidad para darle color de fondo. Podemos construir ese mismo átomo con CSS propio o con Tailwind y reutilizarlo dentro de una molécula, como un formulario de búsqueda.

4.1. Psicología de la Gestalt

La percepción visual es la interpretación activa que realiza el cerebro de los estímulos lumínicos. La escuela alemana de la Gestalt ("forma" o "configuración") formuló leyes psicológicas que explican cómo la mente agrupa visualmente elementos individuales para percibir un "todo" estructurado.

Figura 1.3: Leyes de la Gestalt aplicadas al agrupamiento y percepción visual en pantallas.

4.1.1. Principales leyes de la Gestalt aplicadas a UI

  • Ley de Proximidad: Los objetos colocados cerca unos de otros se perciben como un grupo unificado. UI: Las etiquetas de entrada de formularios se colocan pegadas a sus campos correspondientes.
  • Ley de Semejanza (Similitud): Elementos con forma o color igual se perciben como pertenecientes a la misma categoría. UI: Botones primarios del mismo color.
  • Ley de Cierre (Clausura): La mente tiende a completar figuras incompletas. UI: Tarjetas de carrusel recortadas en el borde para sugerir desplazamiento.
  • Ley de Continuidad: El ojo sigue una trayectoria fluida. UI: Listas de elementos alineadas verticalmente.
  • Ley de Figura y Fondo: Separamos el objeto destacado del espacio circundante. UI: Modales con fondo oscurecido (overlay).
  • Ley de Simetría y Orden (Prägnanz): El cerebro simplifica formas complejas. UI: Maquetación en cuadrículas o retículas.
  • Ley de Región Común: Elementos delimitados por un borde cerrado se perciben como un conjunto. UI: Tarjetas (cards).
  • Ley de Destino Común: Elementos que se desplazan juntos se perciben unificados. UI: Menús desplegables animados.

4.3.2. Imágenes para la web

La codificación de imágenes estáticas se puede realizar de formas: mediante mapas de bits (indicando para cada bit de la pantalla su color) o mediante representación vectorial (Indicando únicamente los vértices y color de cada polígono que queramos generar).

Cada pixel se representará utilizando una escala de color RGB (Red, Green and Blue) o CMYK (Cyan, Magenta, Yellow, blacK -para impresoras-) reduciendo así a tres números (4 en el caso de impresión) que simbolizan la cantidad de cada color que se van a mezclar para generar el color resultante.

A los colores en pantalla se les puede incorporar un cuarto valor que representa la transparencia de la imagen, y que es conocido como el “canal Alfa”.

También es frecuente comprimir las imágenes para que ocupen menos tamaño reduciendo la profundidad de color, la resolución de la imágen, o el número de pixeles a representar mediante la aproximación de zonas de bits de igual color.

Un video siempre se va a formar a partir de imágenes estáticas, siendo importante el número de imágenes (marcos) que se representan FPS y teniendo en cuenta que la compresión también se puede realizar mediante transiciones entre imágenes, es decir, manteniendo los elementos que no cambian y guardando información de los que sí.

4.3.2.1. Profundidad de color

La profundidad de color indica cuántos bits se utilizan para codificar el color de cada píxel. Con n bits por píxel se pueden representar hasta 2n valores distintos. Por ejemplo, 1 bit permite 2 colores y 8 bits permiten 256 valores, que pueden corresponder a tonos de gris o a colores de una paleta.

En una imagen RGB de 24 bits por píxel, cada canal (rojo, verde y azul) utiliza 8 bits: 256 niveles, del 0 al 255. Al combinar los tres canales se obtienen 256 × 256 × 256 = 16.777.216 colores posibles. Por eso hay que distinguir entre bits por píxel y bits por canal.

Una mayor profundidad permite representar más matices y reduce los saltos visibles en los degradados (banding). No aumenta la resolución: la resolución indica cuántos píxeles tiene la imagen; la profundidad indica cuántos valores de color puede representar cada uno. A igual resolución y sin compresión, más bits por píxel requieren más espacio de almacenamiento.

¿Y las imágenes de 32 bits? En un formato habitual, RGBA de 32 bits, se emplean 24 bits para el color y otros 8 para el canal alfa (transparencia). Esos 8 bits adicionales no aumentan el número de colores RGB.

4.5.2. Logotipo

El signo de marca permite identificar quién ofrece el producto o servicio. Aunque a menudo se llama «logo» al conjunto, conviene distinguir estas cuatro formas de representación:

Figura 1.4: Clasificación técnica de marcas visuales para diseño de identidades digitales.
  • Logotipo: Representación basada únicamente en texto/tipografía (ej. Google).
  • Isotipo: Símbolo gráfico independiente sin texto (ej. la manzana de Apple).
  • Imagotipo: Unión de icono y texto que pueden funcionar de forma independiente.
  • Isologotipo: Integración indivisible de texto y símbolo gráfico dentro de una figura unificada.

Al incorporarlo a una web, respeta sus proporciones, el área de protección y las versiones autorizadas para fondos claros y oscuros. Comprueba que se reconoce en tamaños pequeños; una versión reducida o un favicon requiere una adaptación prevista, no un recorte arbitrario.

Conserva un original vectorial cuando corresponda. Si el logotipo enlaza al inicio, su nombre accesible debe comunicar ese destino, por ejemplo «Migas Amigas, inicio».

4.5.2.1. Icono de página o favicon

El favicon es el pequeño icono que identifica una web en la pestaña del navegador y en los marcadores. Ayuda a reconocerla entre otras páginas abiertas. El nombre describe su función; .ico es uno de los formatos que puede utilizar. También pueden emplearse imágenes PNG o SVG.

Del logotipo al favicon: no reduzcas sin más todo el nombre de la panadería. En Migas Amigas puedes utilizar una espiga simplificada, la silueta de un pan o las iniciales «MA», manteniendo los colores y rasgos de la marca.

  1. Selecciona lo esencial: parte del símbolo del imagotipo o crea una versión abreviada del logotipo. Elimina eslóganes, trazos finos y detalles que desaparezcan al reducirse.
  2. Prepara una composición cuadrada: centra el dibujo, deja margen alrededor y comprueba su contraste sobre fondos claros y oscuros. Conserva un original de buena calidad antes de generar las versiones pequeñas.
  3. Prueba el tamaño real: revisa el resultado a 16 × 16 y 32 × 32 píxeles, sin ampliar la vista. Si el símbolo no se reconoce, simplifícalo antes de exportarlo.
  4. Genera los archivos: exporta un PNG y utiliza un generador para preparar el archivo ICO y las variantes necesarias. Un ICO puede contener varias resoluciones. Cambiar la extensión de un PNG a .ico no convierte el formato.

4.5.3. Iconografía

Los iconos representan acciones, objetos o estados. Elige símbolos reconocibles para tu público —como una lupa para buscar— y acompáñalos de texto cuando su significado pueda resultar ambiguo. Un icono de interfaz cumple una función distinta del símbolo que identifica una marca.

5.1. Boceto en papel o sketch: explorar ideas

El sketch es un dibujo rápido a mano alzada, normalmente sobre papel. No requiere saber dibujar: bastan rectángulos para los bloques, líneas para el texto y flechas para indicar recorridos. Su objetivo es comparar alternativas con poco esfuerzo.

  • Cómo hacerlo: define una tarea del usuario, dibuja dos o tres distribuciones y anota qué ocurre al pulsar las acciones principales.
  • Qué comprobar: si aparecen los contenidos necesarios, qué destaca primero y si se entiende cómo avanzar.
  • Ejemplo en Migas Amigas: dibuja la portada móvil con la marca, los productos destacados y el acceso a un encargo. Prueba distintas posiciones para la acción principal.

Para probar el recorrido, otra persona puede señalar dónde pulsaría mientras tú sustituyes una hoja por la siguiente pantalla. Guarda una foto del boceto elegido y anota los cambios acordados.

5.2. Wireframe: organizar la estructura

El wireframe es un esquema más preciso de la distribución y la jerarquía del contenido. Suele utilizar grises, cajas y textos sencillos para centrar la revisión en la organización. Puede elaborarse en papel o con una herramienta digital.

  • Qué definir: cabecera, navegación, bloques de contenido, campos, botones y relaciones entre pantallas. Prepara las vistas móvil y escritorio cuando su distribución cambie.
  • Qué comprobar: si los nombres de los enlaces se entienden, si la información está bien agrupada y si se encuentra la acción principal.
  • Ejemplo en Migas Amigas: concreta dónde van el nombre, la imagen y el precio de cada producto, y cómo se accede a su detalle o al formulario de encargo.

El resultado es un conjunto de pantallas estructuradas. Un wireframe puede ser estático o enlazarse para ensayar la navegación; todavía no necesita fotografías ni acabados visuales definitivos.

6. Metodología Design Thinking

El proceso de diseño y desarrollo de productos digitales centrados en las personas se fundamenta en la metodología Design Thinking (Pensamiento de Diseño). Esta metodología ágil, iterativa y no lineal se articula en 5 etapas consecutivas: Empatizar, Definir, Idear, Prototipar y Testar.

Figura 1.10: Ciclo metodológico de las 5 fases de Design Thinking en proyectos de interfaces digitales.

Naturaleza iterativa del Design Thinking

A diferencia de los modelos tradicionales en cascada, el Design Thinking es profundamente iterativo y flexible. Al testar un prototipo en la fase 5 con usuarios reales, los hallazgos pueden revelar que el problema no estaba bien definido (lo que obliga a volver a la fase 2) o que se requieren nuevas soluciones (fase 3). Este bucle de realimentación continua reduce exponencialmente el riesgo de desarrollar software que nadie desea o que resulta imposible de usar.

6.1. Profundización en las 5 Fases del Design Thinking

Fase 1: Empatizar (Comprender al Usuario en su Contexto)

El objetivo de esta fase es sumergirse en la realidad de las personas usuarias para comprender sus necesidades profundas, motivaciones, patrones de conducta, emociones y puntos de dolor (pain points). Se evita presuponer o imponer la visión del desarrollador.

  • Entrevistas en Profundidad: Conversaciones semiestructuradas para explorar cómo el usuario resuelve sus tareas actualmente.
  • Observación Contextual (Shadowing): Estudio directo del usuario en su entorno natural utilizando herramientas digitales o físicas.
  • Mapa de Empatía (Empathy Map): Matriz visual que organiza lo que el usuario Dice, Piensa, Hace y Siente, identificando sus esfuerzos (frustraciones) y sus resultados (metas).

Fase 2: Definir (Sintetizar el Problema y Encuadrar la Solución)

Se analiza la información cualitativa y cuantitativa recopilada durante la empatía para identificar el problema central desde la perspectiva del usuario (Point of View - POV). Se formulan preguntas clave del tipo "¿Cómo podríamos...?" (How Might We - HMW).

  • User Personas: Arquetipos de usuarios ficticios construidos con datos reales que resumen objetivos, contexto demográfico y frustraciones.
  • Customer Journey Map: Mapa del viaje del usuario que documenta la secuencia de interacción antes, durante y después del uso de la aplicación, identificando puntos críticos de caída.
  • Card Sorting (Clasificación de Tarjetas): Pruebas abiertas o cerradas donde usuarios reales agrupan contenidos en categorías para descubrir su modelo mental.
  • Tree Testing: Prueba de árbol de contenido sin elementos visuales para validar si la estructura de menú propuesta es comprensible.

Fase 3: Idear (Generar Alternativas Creativas y Definir la Guía de Estilo)

En la fase de ideación se fomenta la generación masiva de ideas y soluciones sin juzgarlas prematuramente. Una vez seleccionadas las mejores ideas, se traducen en la arquitectura visual e identidad del proyecto.

  • Brainstorming y SCAMPER: Técnicas de dinamización grupal para diversificar las propuestas de interfaz y navegación.
  • Definición de la Guía de Estilo: Confección de la identidad visual, paleta semántica, escala tipográfica y Design Tokens estudiados en el apartado 7.
  • Arquitectura de Información (IA): Elaboración del mapa de navegación que organiza los flujos y las pantallas principales de la aplicación web.

Fase 4: Prototipar (Dar Forma Tangible a las Ideas)

Se construyen representaciones tangibles de las soluciones para que el usuario o cliente pueda interactuar con ellas. El prototipado es progresivo y rápido para no invertir recursos excesivos antes de validar la idea.

  • Prototipos de Baja Fidelidad (Wireframes): Esquemas estáticos en blanco y negro (realizados en papel o con herramientas como Wireframe.cc) centrados exclusivamente en la distribución de la información.
  • Prototipos de Alta Fidelidad (Mockups en Figma): Pantallas con diseño estético completo aplicando la guía de estilo y el sistema Atomic Design.
  • Prototipos Funcionales Interactivos: Maquetación interactiva con enlaces, transiciones y componentes que simulan la lógica real del sistema.

Fase 5: Testar (Evaluar, Medir e Iterar con Usuarios)

Se somete el prototipo funcional a pruebas reales con usuarios representativos para observar cómo interactúan, detectar problemas de usabilidad, medir tiempos de ejecución de tareas y recopilar retroalimentación directa.

  • Pruebas de Usabilidad Moderadas / No Moderadas: Sesiones donde el usuario ejecuta tareas clave (ej. realizar una compra) mientras piensa en voz alta (Think Aloud Protocol).
  • Auditoría Heurística de Nielsen: Evaluación experta mediante los 10 principios de usabilidad explicados en el apartado 2.3.4.
  • Auditoría de Accesibilidad WCAG 2.2: Comprobación de ratios de contraste, foco por teclado, compatibilidad con lectores de pantalla y Target Size.
  • Medición de Rendimiento Visually-Perceived (Core Web Vitals): Verificación de métricas LCP, INP y ausencia de saltos visuales (CLS).

7. Guía de estilo y diseño de interfaces web

Una guía de estilo web —también denominada manual de look and feel o manual de interfaz visual— documenta las decisiones visuales, verbales, tipográficas, cromáticas e interactivas de un producto digital. Su finalidad es que diseñadores, desarrolladores frontend, redactores de contenido (UX Writers) y futuras personas encargadas del mantenimiento apliquen criterios estandarizados y coherentes sin tener que reinterpretar la marca en cada nueva pantalla o módulo.

7.1. Finalidad, alcance y contenidos esenciales

La guía debe ser suficientemente precisa para producir resultados consistentes en diferentes dispositivos y suficientemente flexible para evolucionar con el producto. 7.2. Proceso de creación en siete pasos

En el laboratorio de Migas Amigas seguimos este mismo orden. Cada paso consiste en observar un ejemplo, elegir y justificar una decisión, y comprobarla en la maqueta. El proceso termina con una prueba entre compañeros y una mejora documentada.

  1. Paso 1

    Definir la identidad: concretar misión, visión, valores, personalidad y atributos comunicativos que la interfaz debe transmitir.

  2. Paso 2

    Construir la paleta cromática: seleccionar colores primarios, secundarios, neutros y de estado semántico, indicando cuándo se aplica cada uno con sus ratios WCAG.

  3. Paso 3

    Establecer el sistema tipográfico: elegir familias legibles en el contexto real de uso y definir una escala proporcional coherente.

  4. Paso 4

    Regular las imágenes y gráficos: determinar estilo, relaciones de aspecto, encuadre, compresión, optimización de rendimiento y alternativas textuales.

  5. Paso 5

    Estandarizar la iconografía: escoger una familia coherente, rejilla vectorial, tamaños estandarizados y reglas de accesibilidad ARIA.

  6. Paso 6

    Definir tono y estilo de escritura (UX Writing): fijar formalidad, terminología, voz activa, lenguaje inclusivo y redacción de mensajes del sistema.

  7. Paso 7

    Especificar componentes UI: documentar botones, campos de entrada, tarjetas y modales con anatomía, variantes, estados interactivos y código CSS.

8. Sistemas de diseño

Guía de estilo frente a sistema de diseño

La guía de estilo describe y norma las reglas visuales: identidad corporativa, paleta cromática, tipografía, estilo fotográfico, iconografía, tono de voz y comportamiento interactivo. Por su parte, un sistema de diseño amplía esa documentación técnica integrando Design Tokens, componentes de código reutilizables (React, Vue, Web Components), patrones de interacción, pruebas de accesibilidad y mecanismos de gobernanza. Por ello, la guía constituye la base normativa dentro del sistema de diseño.

8.1. De la guía al sistema de diseño

La guía de estilo recoge las decisiones de diseño y explica cómo aplicarlas: qué colores y tipografías utilizar, cómo presentar la marca y qué aspecto y comportamiento deben tener los elementos de la interfaz. Es una parte del sistema de diseño y sirve de referencia para construir sus recursos.

El sistema de diseño amplía esa guía con tokens, componentes reutilizables en las herramientas de diseño y en el código, patrones de interacción y documentación de uso. También establece responsables y procesos de revisión para mantener todas esas piezas coordinadas. Así, las reglas de la guía se convierten en soluciones que el equipo puede utilizar de forma consistente en distintas pantallas.

Por ejemplo, la guía especifica cómo debe ser un campo de formulario: etiqueta visible, tipografía, borde y mensaje de error. El sistema proporciona el componente de campo con esas características y sus estados preparados para reutilizarlos en contacto o al finalizar un pedido. Si cambia una regla, se revisan conjuntamente la guía y el componente.

AspectoGuía de estiloSistema de diseño

RecursosNormas y ejemplos de uso.También tokens, componentes implementados y patrones.
MantenimientoRevisión de la documentación.Versionado, pruebas y evolución conjunta del diseño, código y documentación.

8.2. Cuándo conviene y cómo empezar

Una guía puede bastar para un producto acotado y un equipo pequeño. Conviene avanzar hacia un sistema cuando aparecen componentes duplicados, incoherencias recurrentes o varios equipos y productos que necesitan compartir soluciones. Su mantenimiento exige dedicación.

  1. Tokens: convertir decisiones repetidas en valores compartidos.
  2. Componentes: implementar primero los más utilizados, con variantes y estados.
  3. Patrones y documentación: explicar cómo combinarlos y cuándo utilizarlos.
  4. Gobernanza: asignar responsables, revisar aportaciones y publicar versiones con sus cambios.
Un sistema se mantiene como un producto

La lectura de Midrocket destaca una diferencia de inversión: mantener un sistema implica atender nuevas necesidades, dependencias y correcciones de accesibilidad. No basta con entregar una biblioteca una vez. La dificultad para incorporar nuevos miembros y el esfuerzo repetido en interfaces habituales son otras señales para plantear esa evolución.

9. Errores frecuentes

Principales fallos en diseño UI/UX

  • Eliminar el borde de foco (`outline: none`): Ocultar el estado de foco destruye la accesibilidad por teclado (WCAG 2.4.7).
  • Sustituir la etiqueta ` El placeholder desaparece al escribir, confundiendo al usuario y violando la accesibilidad en formularios.
  • Provocar inestabilidad visual (Layout Shift - CLS): Cargar imágenes o banners sin definir `width` y `height`, provocando que el texto dé saltos al cargar la web.
  • Confundir mapa de navegación con `robots.txt`: Pensar que `robots.txt` crea menús. Solo da directivas de acceso a spiders.
  • Prescindir de los estados UI: Diseñar componentes únicamente en estado de reposo (*Default*) ignorando los estados *Hover*, *Focus*, *Active* y *Disabled*.

11. Resumen

Figura 1.15: Síntesis de los pilares metodológicos y técnicos del Tema 1 para la creación de software web profesional.

Ideas clave

  1. La evolución del diseño web pasa de documentos enlazados y textuales a sistemas interactivos, adaptativos y multidispositivo; cada cambio visual está condicionado por la tecnología y el contexto de uso.
  2. Los hitos esenciales incluyen el nacimiento de la Web (1989–1991), la estandarización mediante W3C, la incorporación de JavaScript y CSS, la Web 2.0 y el diseño responsivo formulado en 2010.
  3. Tipografías expresivas, SVG, scroll narrativo, WebXR, neomorfismo y grandes recursos visuales solo son adecuados si preservan utilidad, accesibilidad, rendimiento y coherencia.
  4. La UI aborda elementos visuales; la UX la experiencia global de usabilidad.
  5. Las GUI operan bajo el paradigma Objeto-Acción.
  6. Los principios de usabilidad exigen respuesta y feedback claros, funciones relevantes, legibilidad, consistencia, navegación comprensible, recuperación de errores y protección del trabajo del usuario.
  7. Las reglas de los dos segundos, los tres clics y el 7 ± 2 son heurísticas orientativas: deben validarse con métricas y pruebas de usuario, no aplicarse como límites absolutos.
  8. La accesibilidad WCAG exige ratios de contraste numérico: 4.5:1 (texto normal) y 3:1 (texto grande y componentes UI).
  9. Las Leyes de la Gestalt y las Leyes de UX rigen la organización perceptiva e interactiva.
  10. Las marcas se clasifican en Logotipo, Isotipo, Imagotipo e Isologotipo.
  11. Los elementos de relación —dirección, posición, espacio y gravedad visual— organizan el recorrido de la mirada, la ubicación, la separación y el peso perceptivo de las formas.
  12. Atomic Design organiza la UI en Átomos, Moléculas, Organismos, Plantillas y Páginas mediante Design Tokens.
  13. La guía de estilo es un documento vivo que normaliza identidad, color, tipografía, imágenes, iconos, tono de voz y comportamiento de componentes.
  14. Un sistema de diseño amplía la guía mediante tokens, componentes reutilizables, código, versionado y un proceso de gobernanza.
  15. Todo componente UI interactivo debe definir sus 6 estados (Default, Hover, Focus, Active, Disabled, Loading) respetando el foco por teclado (WCAG 2.4.7).
  16. La estrategia Mobile-First requiere áreas táctiles mínimas (Target Size de 24px WCAG / 44-48px recomendado).

13. Planificación del proyecto web

Planificar consiste en acordar qué se entregará, quién lo hará, con qué recursos y en qué plazo. El proceso de Alberto del Río conecta briefing, alcance, estimación, diseño, pruebas y comunicación continua. En Migas Amigas ya tenemos entrevista, mapa, wireframes y decisiones visuales: conviértelos en tareas y entregables verificables.

  • Acota el alcance: guía de estilo completa y prototipo navegable en Figma, con móvil y escritorio. La programación y los pagos reales quedan fuera de esta entrega.
  • Desglosa y estima: para cada tarea anota responsable, esfuerzo en horas, fechas y resultado esperado. Dos horas de trabajo no equivalen necesariamente a dos horas de calendario: cuenta la disponibilidad y las esperas.
  • Ordena y revisa: identifica dependencias y fija hitos, como «wireframes revisados» o «prototipo probado». Reserva margen para correcciones y comunica bloqueos o cambios de alcance; revisa el plan con lo aprendido en las pruebas.

Un diagrama de Gantt representa las tareas como barras sobre un calendario y muestra duraciones, solapamientos y dependencias. Un tablero Kanban permite seguir su estado: «Pendiente → En curso → En revisión → Hecho», limitando el trabajo simultáneo. Puedes combinar ambos: Gantt para prever plazos y Kanban para gestionar el avance. Trabajar de forma ágil implica revisar prioridades y mejorar mediante entregas pequeñas; no significa improvisar ni prescindir de la planificación.

Ejemplo: revisar el mapa → completar wireframes → aplicar la guía al mockup → conectar el prototipo → probar y corregir. La documentación de la guía se actualiza en paralelo al diseño. Una tarea estará terminada cuando cumpla sus criterios: por ejemplo, «contacto móvil y escritorio, con etiquetas y estados revisados».

14. Análisis de la web

La revisión técnica de un sitio web debe combinar varias perspectivas: validez del código, accesibilidad, seguridad, comportamiento, rendimiento y visibilidad en buscadores. Ninguna herramienta automatizada garantiza por sí sola la calidad o el cumplimiento; sus resultados deben interpretarse y completarse con inspección manual y pruebas con usuarios.
